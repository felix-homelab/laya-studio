# Deployment

## The one-command path

```bash
docker compose up --build      # http://localhost:8000
```

That starts PostgreSQL, applies the migrations, and brings up the panel with real
Laya checkpoints. Mount a Hugging Face cache so the weights are fetched once rather
than on every rebuild.

For anything beyond a look around, keep reading.

## What the image contains

One image. Laya is the only engine, so torch and `laya` are not optional — a panel
without them cannot evaluate anything.

| | |
|---|---|
| Base | `python:3.12-slim` |
| Size | ~2.5 GB, dominated by torch |
| Weights | **not** baked in — mounted at `/models` |

**Why the weights are not in the image.** They are ~400 MB for the English
checkpoint and ~400 MB more for multilingual. Baking them in would mean a rebuild
re-downloads them, and a `docker push` of the image carries them to everyone.

Instead, mount a Hugging Face cache:

```bash
HF_CACHE=~/.cache/huggingface docker compose up --build
```

The first start downloads; every restart after that reads from the mount. Without
the mount, each `--build` pays for it again.

### CUDA

The default index URL installs CPU-only torch. For CUDA:

```bash
TORCH_INDEX_URL=https://download.pytorch.org/whl/cu124 \
HF_CACHE=~/.cache/huggingface docker compose up --build
```

You also need the NVIDIA container toolkit and a GPU reservation on the `app`
service — the block is commented into `docker-compose.yml`:

```yaml
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]
```

`LAYA_STUDIO_LAYA_DEVICE=auto` lets Laya pick cuda → mps → cpu, and it falls back to
CPU itself with a warning if the accelerator it finds does not work.

### Apple Silicon

Run natively rather than in a container — torch on macOS has no CUDA and passing
through MPS is more trouble than it saves:

```bash
pip install -r requirements.txt
LAYA_STUDIO_LAYA_DEVICE=mps python -m uvicorn app.main:app
```

MPS measured ~34 ms for a single question. `auto` also resolves to MPS, so the
setting is only needed if you want to be explicit.

### Pre-fetching weights for an air-gapped install

```bash
# On a machine with network access
huggingface-cli download convaiinnovations/laya --local-dir ./models/laya

# Then
HF_CACHE=./models docker compose up --build
```

Set `LAYA_STUDIO_LAYA_OFFLINE=true` and the runtime will never attempt a network
call.

## PostgreSQL

Required. There is no SQLite path.

`docker compose up` starts three services:

| Service | Image | Role |
|---|---|---|
| `db` | `postgres:16-alpine` | The database, on a named volume |
| `migrate` | `node:22-slim` + Prisma | Runs `prisma migrate deploy` and exits |
| `app` | the panel | Waits for `db` to be healthy and `migrate` to succeed |

The migration step is its own service because it needs Node, and the application
image deliberately does not carry a JavaScript runtime. The app waits on
`service_completed_successfully`, so a failed migration stops the deployment
instead of starting against a stale schema.

```bash
docker compose up --build        # db → migrate → app
docker compose run --rm migrate  # re-apply after a pull, without restarting the app
docker compose logs migrate      # what the last migration run did
```

### Using an external database

Point the DSN at your own server and drop the `db` service:

```bash
export LAYA_STUDIO_DATABASE_URL="postgresql://user:pass@host:5432/laya_studio"
npx prisma migrate deploy       # apply the schema
docker compose up -d app
```

The `laya` role needs `CREATE`, `USAGE` and table ownership in the target schema,
plus `CREATEDB` **only** if you intend to run `prisma migrate dev` against it
(`migrate dev` needs a shadow database; `migrate deploy` does not).

### Migrations in CI

```bash
npm ci
npx prisma migrate deploy
npx prisma migrate status       # exits non-zero if anything is unapplied
```

`migrate deploy` never generates SQL and never resets data — it applies exactly the
committed files. That is the right command for a pipeline. `migrate dev` is a
development tool and will offer to reset the database; do not run it in production.

### Backups

`pg_dump` as normal. Two things are worth knowing about what is in there:

* **`evaluations.label` is the calibration history.** Rows without a label can be
  regenerated by re-running a batch; labelled rows cannot. Back those up.
* **`_prisma_migrations` is the migration ledger.** Restore it with the data, or
  `prisma migrate` will try to re-apply migrations that are already reflected in the
  schema and fail.

```bash
pg_dump --format=custom -d "$DATABASE_URL" -f "laya-$(date +%F).dump"
```

### Schema changes

Development:

```bash
# 1. Edit prisma/schema.prisma
# 2. Edit app/models.py to match
make db-migrate-dev                 # authors and applies a migration
git add prisma/migrations app/models.py
```

The second step is not optional. `tests/test_schema_drift.py` migrates a scratch
database with Prisma and compares the result against `app/models.py` column by
column, so a mismatch is a test failure with a precise diff rather than a runtime
surprise.

Review the generated SQL before committing it — Prisma is good at this but it is
still generating DDL, and a column drop is a data loss.

## Hardening

The panel is an **operator tool with no authentication of its own**, except for
the ingestion token. Treat it the way you would treat a Grafana instance:
internal, behind your existing access control.

Read this list before exposing it.

**1. Set the ingestion token.** Ingestion is the only surface designed for third
parties to call, and it is the one that can trigger outbound webhooks.

```bash
export LAYA_STUDIO_INGEST_TOKEN=$(openssl rand -hex 32)
```

**2. Leave the webhook allow-list empty unless you need it.** By default a webhook
step cannot reach any private, loopback or link-local address — including the
cloud metadata service at `169.254.169.254`. This is what stops an open ingestion
endpoint from becoming an SSRF primitive against your internal network.

```bash
# Only add hosts you control and genuinely need reachable:
export LAYA_STUDIO_WEBHOOK_ALLOWED_HOSTS=internal-api.corp.example
```

Never add `169.254.169.254`.

**3. Put it behind a reverse proxy with auth.**

```nginx
location / {
    auth_request /oauth2/auth;      # or your SSO of choice
    proxy_pass http://laya-studio:8000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 300s;        # bulk uploads run synchronously
}
```

`proxy_read_timeout` matters: a bulk job holds the request open.

**4. Lock down the MCP endpoint.** It can read the logs *and* create, run and delete
the panel's data, so an exposed `/mcp` is worse than an exposed UI.

```bash
export LAYA_STUDIO_MCP_TOKEN=$(openssl rand -hex 32)
# or turn it off entirely:
export LAYA_STUDIO_MCP_ENABLED=false
```

The endpoint refuses requests from a `Host` header it has not been told about (421),
which stops a page in someone's browser from reaching it through a rebound hostname.
Loopback and the container name are always accepted; a reverse proxy or a LAN
address has to be declared:

```bash
export LAYA_STUDIO_MCP_ALLOWED_HOSTS=panel.internal,10.0.0.5
```

The panel logs a warning at startup while the endpoint is unauthenticated and the
environment is not `development`. See
[observability-and-mcp.md](observability-and-mcp.md#security).

**5. Decide what the logs are allowed to contain, and for how long.**
`/api/observability/*` returns log messages and tracebacks, and a traceback carries
whatever the failing code had in hand. Gate it, or turn the sink off:

```bash
export LAYA_STUDIO_OBSERVABILITY_TOKEN=$(openssl rand -hex 32)
export LAYA_STUDIO_LOG_RETENTION_DAYS=7    # 0 disables pruning
export LAYA_STUDIO_LOG_JSONL=false         # stderr only; nothing on disk
```

**6. Confirm the engine loaded.**

```bash
docker exec laya-studio python -m app.cli check
curl -s localhost:8000/api/health | python3 -m json.tool
```

There is no fallback engine, so a broken runtime crashes the container at boot
rather than degrading — but confirm the *checkpoints* loaded, not just the process.
`/api/health` reports `loaded_checkpoints` and `device`.

**5. Change the secret key.**

```bash
export LAYA_STUDIO_SECRET_KEY=$(openssl rand -hex 32)
```

**6. Do not expose the OpenAPI docs** if they are not useful to you. They are
mounted at `/api/docs`, `/api/redoc` and `/api/openapi.json`; block them at the
proxy.

**7. Set `LAYA_STUDIO_ENVIRONMENT=production`** so the UI and logs never look like
a dev instance.

## Health and readiness

```bash
curl -fsS http://localhost:8000/api/health
```

The `Dockerfile` healthcheck uses this. It is a liveness probe — always 200 while
the process is up — and it also reports the engine and row counts, so it doubles
as a quick "is it degraded?" check.

`/api/health` is a **liveness** probe: it returns 200 as soon as the panel is
serving, which is well before the engine is usable. It reports which of the three
states you are in:

```bash
curl -s localhost:8000/api/health | python3 -c 'import json,sys; print(json.load(sys.stdin)["status"])'
# starting  -> the engine is loading; decisions return 503
# ok        -> usable
# degraded  -> the runtime could not be built at all
```

`/api/ready` is the **readiness** probe: 503 until a decision can actually be
served, then 200. Use it for load-balancer or orchestrator routing, otherwise a
replica that answers every evaluation with a 503 is still marked healthy.

```yaml
    healthcheck:
      test: ["CMD", "curl", "-fsS", "http://localhost:8000/api/ready"]
```

**Timings.** The panel answers in under a second. The engine takes as long as
loading `english` and `multilingual` takes, plus one priming forward pass —
measured at **~42 seconds** with a warm cache on an M-series laptop, and minutes on
a cold one while the checkpoints download. The same 42 seconds elapse either way;
the difference is that the panel is diagnosable from the first second rather than
refusing connections. See [ADR 0011](adr/0011-background-engine-startup.md).

The Dockerfile's healthcheck uses `/api/health` with `start_period: 15s`, which is
right for liveness. Raise the interval rather than the start period if you only
want one probe.

## Persistence

| Path | Contents |
|---|---|
| `laya-pgdata` (volume) | The database: schemas, revisions, workflow definitions, review queue, every evaluation and its label |
| `./data` (bind mount) | `/app/data` — upload scratch, and the JSONL log store |
| `/models` | Hugging Face cache |

The database is the thing to back up; see [Backups](#backups). Everything of value
is in it.

`./data` is a **bind mount rather than a named volume** so the logs are readable
from the host (`grep data/logs/*.jsonl`) without `docker exec`. It is still
disposable — nothing durable lives there — but note the ownership: the container
runs as uid `10001`, so on a Linux host give the directory to that user once, or the
panel will log a warning and quietly keep its records on stderr only:

```bash
mkdir -p data && sudo chown -R 10001:10001 data
```

On Docker Desktop for macOS and Windows this is handled for you.

## Air-gapped deployments

Two external dependencies need handling.

**Tailwind CSS** is loaded from `cdn.tailwindcss.com`. For an air-gapped install,
vendor it:

```bash
curl -sL https://cdn.tailwindcss.com/3.4.16 -o app/static/js/tailwind.js
```

then change the script tag in `app/templates/base.html` to
`<script src="/static/js/tailwind.js"></script>`. (A generated stylesheet is
better — see [ROADMAP.md](ROADMAP.md#9-tailwind-is-loaded-from-a-cdn).)

**Laya weights** must be pre-fetched and mounted, with
`LAYA_STUDIO_LAYA_OFFLINE=true` so the runtime never attempts a network call.

The generative fallback obviously cannot work air-gapped unless you point
`LAYA_STUDIO_OPENAI_BASE_URL` at a local OpenAI-compatible server. Without it, the
middle band escalates to review — which still works.

## Scaling

**Vertical first.** Laya is a single forward pass on a ~400M-parameter encoder.
One GPU handles a lot of throughput (103–332 questions/sec published), and because
all questions in a bundle share one pass, the cheapest optimisation is always
"ask more questions per call".

**Threading.** Sync endpoints run on FastAPI's thread pool, and `LayaEngine`
serialises inference behind a lock — the model is not thread-safe. So one process
serves inference one request at a time; concurrency beyond that comes from
queueing, not parallelism.

**Scaling out.** Multiple replicas are safe if they share a database. Each keeps
its own temperature cache for the TTL window, which is correct if slightly
wasteful. The ingestion endpoint is stateless and load-balances cleanly.

**The bottleneck you will actually hit** is bulk uploads, which are synchronous
and hold a request open. See [ROADMAP.md](ROADMAP.md#the-worker-path).

## Monitoring

There is no Prometheus endpoint yet ([ROADMAP.md](ROADMAP.md#5-prometheus-metrics)).
What you can scrape today:

| Signal | Where |
|---|---|
| Liveness, engine, device, checkpoints, row counts | `GET /api/health` |
| Escalation rate | `GET /api/analytics/overview` → `escalation_rate` |
| Calibration drift | `GET /api/analytics/calibration` → `trend`, `ece` |
| Failed actions | `GET /api/analytics/routes` → `action_outcomes` |
| Queue depth | `GET /api/review/stats` → `open` |

**Worth alerting on:**

* `escalation_rate` spiking, or pinned near 1.0 — the model or the data moved.
  Note that a high escalation rate is the *expected* state before calibration;
  see [analytics-and-calibration.md](analytics-and-calibration.md).
* `ece` rising on a stable question — recalibrate.
* `device` changing to `cpu` in `/api/health` — something took the GPU away.
* `review_open` growing without bound — nobody is working the queue, and the
  calibration loop has stopped turning.
* `action_outcomes` showing `webhook:failed` — a downstream integration broke.

## Deployment checklist

```bash
# 1. Secrets
export LAYA_STUDIO_SECRET_KEY=$(openssl rand -hex 32)
export LAYA_STUDIO_INGEST_TOKEN=$(openssl rand -hex 32)

# 2. A real database
export LAYA_STUDIO_DATABASE_URL="postgresql+psycopg://laya:$PGPASSWORD@db:5432/laya_studio"
docker compose --profile postgres up -d

# 4. The generative fallback, or accept that the middle band escalates
export LAYA_STUDIO_LLM_PROVIDER=openai
export LAYA_STUDIO_OPENAI_API_KEY=sk-...

# 5. Model weights, cached on the host
export HF_CACHE=~/.cache/huggingface
docker compose up -d

# 6. Verify
docker compose exec app python -m app.cli check
curl -fsS localhost:8000/api/health | python3 -m json.tool
```

Then confirm, in the UI:

* `/api/health` reports `device: cuda` (or whatever you expect) and both
  auto-routed checkpoints loaded;
* `/analytics` shows your own traffic, not the sample dataset;
* `/review` is empty or contains only real escalations.

If you ran `python -m app.cli load-sample` on this database, purge it first. It
records genuine evaluations, but they are of a sample dataset, and leaving them in
will skew every metric you look at.

```bash
python -m app.cli purge --yes && python -m app.cli init-db
```
